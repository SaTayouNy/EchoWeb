# API персонального избранного

Базовый путь: `/v1/me/preferences`. Все операции требуют `Authorization: Bearer <accessToken>`.
Пользователь определяется исключительно по токену. Передавать `userId` не нужно; он не влияет на владельца записи.
Публичного API чужого избранного нет. Даже администратор через эти маршруты работает только со своим списком.

## Маршруты

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | `/v1/me/preferences?type=movie&page=0&size=20` | `200`, список текущего пользователя |
| GET | `/v1/me/preferences/{type}/{tmdbId}` | `200`, сохранённая запись; `404`, если не сохранена |
| PUT | `/v1/me/preferences/{type}/{tmdbId}` | `200`, добавленная или уже существующая запись |
| DELETE | `/v1/me/preferences/{type}/{tmdbId}` | `204`, в том числе при повторном удалении |

`type`: `movie`, `tv`, `actor`, `director`; в URL и query регистр не важен. В ответах используются `MOVIE`, `TV`, `ACTOR`, `DIRECTOR`.
`tmdbId` — положительный числовой ID TMDB, не внутренний UUID. Для фильма/сериала это ID релиза, для актёра/режиссёра — ID персоны.
Фильм и сериал с одинаковым ID считаются разными релизами. Один человек может быть сохранён отдельно как актёр и как режиссёр.

## Добавление релиза

```http
PUT /v1/me/preferences/movie/603
Authorization: Bearer <accessToken>
```

Тело не требуется. Сервер находит релиз в БД либо загружает карточку из TMDB и сохраняет её.
Клиенту не нужно передавать название, постер или другие данные карточки.

Ответ содержит `preferenceId` (UUID), `type`, `tmdbId`, `createdAt`, `release`, `person`.
У релиза `person=null`, а `release` — полная карточка в формате [`GET /v1/media/{mediaType}/{tmdbId}`](TMDB_API_RU.md),
включая `mediaId`, `title`, `posterUrl`, `releaseYear`, `castDetails` и `crewDetails`.
FE может сразу отрисовать сохранённые релизы без отдельных запросов для каждой карточки.

## Добавление актёра или режиссёра

Сначала FE получает карточку релиза через `/v1/media/movie/603`. ID актёра берётся из `castDetails[].tmdbPersonId`,
ID режиссёра — из `crewDetails[].tmdbPersonId` у участника с `role="Director"`.
Для персоны требуется JSON с релизом-источником:

```http
PUT /v1/me/preferences/actor/6384
Authorization: Bearer <accessToken>
Content-Type: application/json

{
  "sourceMediaType": "MOVIE",
  "sourceTmdbId": 603
}
```

`sourceMediaType`: `MOVIE` или `TV` (в JSON верхний регистр); `sourceTmdbId > 0`.
Для режиссёра используется тот же запрос с `director` в пути и ID режиссёра.
Сервер проверяет наличие персоны и её роль в структурированных credits карточки.
Имя и фотографии берутся с сервера: клиент не может подменить их в теле запроса.

Пример структуры ответа для актёра:

```json
{
  "preferenceId": "8bdbb044-3bed-4d61-8771-14954bcaeaa2",
  "type": "ACTOR",
  "tmdbId": 6384,
  "createdAt": "2026-10-01T11:00:00Z",
  "release": null,
  "person": {
    "tmdbPersonId": 6384,
    "name": "Keanu Reeves",
    "profilePath": null,
    "profileUrl": null
  }
}
```

Поля фотографии могут быть `null`. Имя и ссылки персоны сохраняются как снимок при первом добавлении.
Повторное добавление через другой релиз не создаёт дубль и не меняет этот снимок или дату добавления.
При повторном PUT персоны тело с корректными полями по-прежнему обязательно, но существующая запись возвращается без обращения к TMDB.

Источник выбирается из карточек, доступных через существующий API медиа: список актёров ограничен `app.tmdb.cast-limit`,
список группы — 30 участниками. Сохранение произвольной персоны вне этих credits не поддерживается.
У карточек, закэшированных до V13, credits появляются после обновления через существующий механизм синхронизации медиа.

## Чтение и восстановление состояния

```http
GET /v1/me/preferences?page=0&size=20
Authorization: Bearer <accessToken>
```

Форма ответа:

```json
{
  "items": [],
  "meta": { "page": 0, "size": 20, "total": 0, "totalPages": 0 }
}
```

В `items` находятся описанные выше записи. Необязательный `type` фильтрует список и `total`.
`page` начинается с **0**, `size` — от 1 до 100, по умолчанию 20. Сортировка: сначала новые записи,
при совпадении даты — по `preferenceId` по убыванию. Страница за пределами списка возвращает `200` и пустой `items`.

После входа FE загружает список с новым access token. Для проверки кнопки конкретной карточки можно использовать
`GET /v1/me/preferences/movie/603`: `200` означает «сохранено», `404 PREFERENCE_NOT_FOUND` — «не сохранено».
После logout клиент очищает локальное состояние; серверные предпочтения остаются в БД и доступны при следующем входе в тот же аккаунт.
Чтение, удаление и повторное добавление существующего предпочтения работают без TMDB.

## Ошибки

Ответы используют общий формат `{ "error": { "code": "...", "message": "...", "details": [...] } }`;
`details` может отсутствовать или быть `null`, если ошибка не относится к полям запроса.

| Ситуация | HTTP | Код |
| --- | --- | --- |
| Нет токена, токен неверен, истёк или отозван | 401 | Общий код ошибки авторизации |
| Некорректный JSON, неизвестный тип, нечисловой ID | 400 | `BAD_REQUEST` |
| ID ≤ 0, неверная пагинация, нет полей источника персоны | 422 | `VALIDATION_ERROR` |
| Запись отсутствует при GET | 404 | `PREFERENCE_NOT_FOUND` |
| Персона отсутствует в credits источника или не имеет указанной роли | 404 | `PERSON_NOT_FOUND` |
| Релиза нет в TMDB | 404 | `MEDIA_NOT_FOUND` |
| Неизвестный маршрут | 404 | `NOT_FOUND` |
| Неподдерживаемый метод | 405 | `METHOD_NOT_ALLOWED` |
| Тело передано с неподдерживаемым Content-Type | 415 | `UNSUPPORTED_MEDIA_TYPE` |
| Превышен существующий лимит JSON-тела | 413 | `PAYLOAD_TOO_LARGE` |
| Ошибка TMDB при первой загрузке | 502/503 | Коды из [контракта TMDB](TMDB_API_RU.md) |

Неудачная проверка или загрузка не создаёт запись предпочтения. Загруженная карточка источника при этом может остаться в общем кэше медиа.

## База данных и проверка

Flyway автоматически применяет `V14__user_preferences.sql` при запуске. Таблица `user_preferences` хранит владельца,
тип, TMDB ID, дату, ссылку на `media` для релиза либо снимок персоны. Внешние ключи связывают запись с существующим пользователем
и релизом; уникальность `(user_id, type, tmdb_id)` запрещает дубли на уровне БД. Удаление пользователя удаляет его предпочтения.
Удаление предпочтения сохраняет общую карточку релиза и записи других пользователей.
Мутации одного аккаунта используют блокировку строки пользователя в короткой транзакции; сеть вызывается до получения блокировки.

Миграция не изменяет существующие профильные предпочтения жанров, стран и типов контента из `/v1/me/profile`.

```powershell
mvn test
# Только проверки избранного:
mvn '-Dtest=PreferenceIntegrationTest,PreferenceMigrationTest' test
```

Проверки покрывают четыре типа, повторные и одновременные добавления, удаление, пагинацию, изоляцию аккаунтов,
logout/login, невалидные запросы, ошибки TMDB, CORS PUT, миграцию с V13, ограничения БД и повторное открытие файловой БД.
Интеграционные тесты используют H2 в режиме PostgreSQL и TMDB stub; реальный PostgreSQL и live TMDB здесь не проверяются.
