# Работа с задачей

> **Цель:** единый порядок постановки, выполнения и проверки задач · **Обновлено:** 23.10.2026 · **Ответственный:** Роман Стяжкин (PM)

Задачи ведутся в [GitHub Issues](https://github.com/SaTayouNy/EchoWeb/issues) репозитория EchoWeb. Для разработки и документации это обязательно. Задачи бэкенда можно вести в репозитории бэкенда, но они должны быть на общей доске GitHub Projects.

## Как написать задачу

Создайте issue по шаблону **«Задача (ТЗ)»**: **New issue → Задача (ТЗ)**. Описание — это ТЗ, где чётко сказано:

- **Название** — коротко, глаголом: «Подключить интерфейс к API».
- **Желаемый результат** — что должно получиться и зачем.
- **Требования к результату** — проверяемый список.
- **Формат результата** — что прикрепить: pull request, ссылку, файл, скриншоты.
- **Reviewer** — кто проверяет: человек этой специальности.

### Пример требований (макет)

1. Спроектированы все страницы из функциональной карты.
2. Включены все состояния элементов: скрытые, при наведении, активные.
3. Показаны варианты наполнения: текст разного объёма, картинки разных форматов, отсутствие текста.
4. Анимации и переходы описаны комментариями.
5. Повторяющиеся элементы едины по стилю: одинаковые отступы, шрифты, цвета.
6. Ресурсы (картинки, иконки, шрифты) собраны в отдельный фрейм и готовы к экспорту.
7. Команда понимает макет: все анимации, элементы и решения.

Примеры ТЗ текущего спринта — в [спринте 7](../07-sprints/sprint-07.md).

## Поля задачи

| Поле | В GitHub | Значение |
|---|---|---|
| Исполнитель | Assignees | Кто выполняет задачу |
| Статус | Колонка на доске Projects | См. ниже |
| Приоритет | Метка `приоритет: высокий / средний / низкий / заморожен` | Высокий — первым; низкий — последним; заморожен — пока не нужен |
| Story Point | Метка `SP: 1 / 2 / 3` | 1 — простая, 2 — обычная, 3 — сложная, ресурсоёмкая |
| Оценка времени | В описании, часы | Сколько нужно на выполнение |
| Дата начала / Срок | Milestone спринта + дата в описании | Срок — дата перевода в Done включительно. На Review результат отправляется **раньше** срока |
| Зона | Метка `FE / BE / PM / Дизайн / Docs` | Чья это задача |

## Статусы

`ToDo → In Progress → Review → (Correction → Review) → Done`

1. **Согласование.** До начала исполнитель и PM согласуют ТЗ и срок: нет ли вопросов, за какой срок задачу реально сделать.
2. **In Progress.** Начали работу — перенесите карточку в «In Progress».
   - Сделали часть объёмной задачи — отметьте пункты чек-листа и напишите в комментарии, что готово.
3. **Сверка с ТЗ.** Закончили — сравните результат с требованиями.
4. **Review.** Всё сходится — переведите в «Review» и приложите результат в комментарии в формате из ТЗ. Для кода это pull request со ссылкой `Closes #номер`. Отметьте reviewer.
   - Reviewer просит переделать — уточните, что именно, переведите в «Correction» и запишите в комментарии, **что конкретно** нужно изменить.
5. **Done.** Reviewer одобрил — переведите в «Done» и сообщите PM.

**О каждом переходе между статусами сообщайте PM** — в чате или упоминанием в задаче.

## Как проводить ревью

1. Сравнить результат с ТЗ задачи.
2. Проверить код или документ по чек-листу из шаблона pull request.
3. Одобрить (**Approve**) или запросить изменения (**Request changes**) с конкретными комментариями.
