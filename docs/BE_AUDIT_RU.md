# Аудит бэкенда Echo по ТЗ PM

Дата: 11–12 сентября 2026. Проверена рабочая копия `D:\echo`, ветка `main`, HEAD `750f51d`, **включая существовавшие до аудита незакоммиченные изменения**. Выводы относятся к этой копии, а не к развёрнутому стенду.

**Вердикт: BE частично готов к интеграции с FE; полную приёмку и выпуск сейчас подтвердить нельзя.** Основные операции работают на H2. Вход по имени пользователя и паролю уже реализован. Найдены воспроизводимые дефекты API и аутентификации, отсутствует Flyway-модуль PostgreSQL, а реальная интеграция с TMDB и SMTP не подтверждена. Активный FE подключает аутентификацию и каталог, но ещё не подключает рецензии и обновление сессии.

Задача трактовалась как проверка и выявление необходимых изменений согласно шести пунктам ТЗ. Прикладной код BE/FE и существующая `data/echo` не изменялись. Добавлены отчёт, изолированные сценарии воспроизведения и тесты ошибок HTTP-клиента.

## 3. Внешние интеграции

### TMDB

Найдена одна внешняя HTTP-интеграция BE — TMDB. Клиент поддерживает карточки movie/TV, поиск, popular, trending, recommendations и локализованные данные. Изображения FE получает напрямую с CDN TMDB; реальная загрузка изображений браузером этим аудитом не подтверждалась.

Доступность проверялась запросом без авторизации:

```powershell
curl.exe -sS --connect-timeout 5 --max-time 15 -o target/audit-tmdb-public-response.json -w 'TMDB HTTP %{http_code}\n' 'https://api.themoviedb.org/3/movie/603?language=ru-RU'
```

Результат: соединение не установлено, `HTTP 000`. Это ограничение проверенной среды, **не доказательство глобального сбоя TMDB**. Даже успешный `401` без ключа доказал бы только сетевую доступность, а не работоспособность интеграции с учётными данными проекта. Адрес popular endpoint и Bearer-авторизация сверены с [официальным описанием TMDB](https://developer.themoviedb.org/reference/movie-popular-list).

Без `APP_TMDB_ACCESS_TOKEN` при `provider=http` приложение завершается ещё при старте с `app.tmdb.access-token must be configured when app.tmdb.provider=http`. Валидатор работает корректно. Поэтому обычная команда dev-запуска из README в текущем окружении недостаточна; для автономной разработки нужен явно указанный `APP_TMDB_PROVIDER=stub`.

Локальные HTTP-тесты проверяют реальный `TmdbHttpClient`, а не mock самого клиента:

| Ответ upstream | Ответ/поведение клиента BE |
|---|---|
| JSON 200, gzip JSON 200 | Десериализация успешна — существующие тесты |
| 401/403 | 502 `TMDB_AUTH_FAILED`, без повторения |
| 404 | 404 `MEDIA_NOT_FOUND`, без повторения |
| 429 | 503 `TMDB_RATE_LIMITED`, без повторения |
| 500/503 | 502 `TMDB_UNAVAILABLE`, две попытки |
| 400 | 502 `TMDB_BAD_RESPONSE` |
| Невалидный JSON / пустой ответ | `TMDB_BAD_RESPONSE` |
| Задержка upstream дольше read timeout | 502 `TMDB_UNAVAILABLE` |
| Пустой token при прямом вызове клиента | `TMDB_CONFIGURATION_ERROR`, сетевой вызов не выполняется |

Реальные фильмы, локализация, актуальность рейтингов, квоты и доступность TMDB из целевого окружения требуют повторной проверки с настроенным токеном. Тестовый stub возвращает синтетические данные и не подтверждает существование TMDB ID.

### Почта

SMTP — вторая внешняя интеграция, хотя это не HTTP API. Реальный SMTP host и учётные данные не предоставлены; письма внешним адресатам не отправлялись. Штатные тесты подтверждают формирование писем, email verification, recovery, outbox, повторные попытки и обработку сбоев через in-memory gateway. Это не проверка доставки через SMTP.

В default-профиле `APP_EMAIL_PROVIDER=in-memory` запрещён валидатором вне dev/test. Для стенда требуется явно настроить `smtp`, sender, параметры TLS/авторизации и URL страниц FE для подтверждения и восстановления. README недостаточно ясно описывает эту обязательность.

## 4. BE и БД

Подтверждено:

- Все десять миграций выполняются на новой H2 с последующим `ddl-auto=validate`.
- Заполненная V9 обновляется до V10 без потери существующего пользователя/email.
- V10 разрешает нескольким аккаунтам иметь `email=NULL`.
- Точный дубликат username отклоняется ограничением БД.
- Пользователи, reviews, answers и sessions доступны через бизнес-сценарии; оценки сохраняются и возвращаются с пагинацией.
- Удаление review удаляет связанные answers; прямое удаление user каскадно удаляет его review и answer.
- Данные отдельной файловой H2 сохраняются после закрытия всех соединений и повторного открытия.
- Пароли и сессионные токены хранятся в виде хешей — проверено штатными тестами. Refresh создаёт новую сессию, повтор старого refresh блокирует семейство токенов.

**PostgreSQL не проверена на реальном сервере.** Дополнительно есть конкретный блокер B01, существующий независимо от доступности сервера. H2 в `MODE=PostgreSQL` не заменяет проверку SQL, блокировок и транзакций на PostgreSQL.

Риски, требующие отдельных проверок/изменений:

- `UNIQUE(username)` чувствителен к регистру, а поиск логина использует `IgnoreCase`. Прямая проверка БД сохранила одновременно `AuditCase` и `auditcase`. Последовательная регистрация через API это предотвращает, но проверка перед INSERT не обеспечивает такую гарантию при гонке. Конкурентный HTTP-сценарий не воспроизводился; подтверждена несовместимость ограничения БД с логикой поиска. Нужна миграция уникального канонического логина и предварительная проверка уже существующих дубликатов.
- Лимит активных сессий использует read-then-write без блокировки пользователя. Штатный тест проверяет последовательные входы; конкурентное превышение лимита остаётся риском.
- В `MediaPersistenceService.findOrCreatePlaceholder` повтор после unique violation использует `TransactionTemplate` с default propagation, а вызывающий `ReviewService.createReview` уже транзакционный. На PostgreSQL после ошибки INSERT текущая транзакция может быть непригодна для повторного чтения. Нужен отдельный конкурентный тест двух первых рецензий на один фильм и повтор в новой транзакции/upsert при подтверждении. Это вывод по коду, не воспроизведённая ошибка PostgreSQL.
- Очистка старых sessions и истёкших verification/recovery tokens по расписанию не найдена; таблицы будут накапливать записи. При очистке sessions нужно сохранить необходимое окно обнаружения повторного refresh.
- Flyway сообщает, что используемая H2 новее проверенной им версии. Миграции прошли; предупреждение следует учесть при согласовании версий.

## 7. Готовность к FE и контракт для подключения

**Активная точка входа — `frontend/src/main.tsx` → `App.tsx`.** Неиспользуемые шаблонные `router.tsx`, `queries/*` и `schemas/api.ts` не следует считать реальным текущим API-клиентом. Они содержат `/api/users`, `/api/posts`, несовместимую user/error schema и чтение JSON даже для 204, но по текущему графу импортов не участвуют в основном приложении. Это технический долг, а не доказательство поломки работающего login.

В активном приложении подтверждены по коду запросы регистрации, login, `/v1/me` после входа, logout, email confirmation, поиска и каталога TMDB. `postJson` корректно обрабатывает 204. Dev-прокси Vite направляет `/v1` на BE:3000; `VITE_API_URL` задаёт отдельный API origin. CORS для `http://localhost:5173` прошёл, неизвестный origin отклонён. Для production нужно настроить origin FE или reverse proxy; браузерная production-проверка не выполнялась.

| Назначение | Контракт BE |
|---|---|
| Register | `POST /v1/auth/register`, JSON `{username,password,email?}`; 201 `{user,tokens?,emailVerificationRequired}`. Без email tokens выдаются сразу; с email — после подтверждения |
| Login | `POST /v1/auth/login`, `{username,password}` или `{email,password}`; 200 `{tokenType,accessToken,refreshToken}`. Если переданы оба идентификатора, username имеет приоритет |
| Private user | `GET /v1/me`, `Authorization: Bearer <accessToken>`; email может быть `null` |
| Public user | `GET /v1/users/{UUID}` → только `{userId,username}` |
| Refresh | `POST /v1/auth/refresh`, `{refreshToken}` → новая пара; старую пару нужно заменить целиком, параллельные refresh недопустимы для FE |
| Logout | `POST /v1/auth/logout` с access → 204; JSON body ответа нет |
| Media | `GET /v1/media/movie/{tmdbId}` или `/tv/{tmdbId}`; UUID `mediaId` и внешний числовой `tmdbId` — разные идентификаторы |
| Lists from TMDB | `{items,page,totalPages,totalResults}`; page начинается с 1 |
| Reviews | `GET /v1/reviews?tmdbMovieId=603&mediaType=movie&userId=...&limit=20&offset=0&sort=createdAt&order=desc`; `{items,meta:{limit,offset,total}}` |
| Review write | `POST /v1/reviews`, `{tmdbMovieId,mediaType:"MOVIE",rating:8,reviewText:"..."}`; PATCH и DELETE по UUID |
| Answers | GET/POST `/v1/reviews/{reviewId}/answers`, PATCH/DELETE `/v1/answers/{answerId}` |
| Error | `{error:{code,message,details?}}`; validation — 422, JSON/type errors — 400, auth — 401, forbidden/unverified — 403, conflict — 409, local limit — 429 |

Остальные ограничения интеграции:

- `/v3/api-docs`, Swagger UI и actuator доступны только ADMIN. Это защита, а не дефект; для FE нужен экспорт OpenAPI либо выданная тестовая admin-сессия. В `OpenApiConfig` не описана Bearer security scheme, что снижает пригодность документации для генерации клиента и Swagger authorization.
- `App.tsx` отключает TypeScript-проверку через `@ts-nocheck`. 15 FE-тестов покрывают шаблонные компоненты, а не фактические auth/media/review сценарии `App.tsx`. Успешная сборка не означает browser E2E.
- Рецензии, избранное и редактирование профиля не следует смешивать: reviews API есть, favorites хранятся только в памяти FE, отдельного BE API избранного и обновления user profile нет.
- Фильтр FE по стране не может полноценно работать на поисковой выдаче: search response не содержит countries; они есть в detail response. Нужно обогащение карточек или согласование серверного поиска/фильтрации.
- Восстановление пароля на FE и обработка `/reset-password` в активном приложении не найдены. Для аккаунтов без email серверный email recovery неприменим.
- `README.md` устарел: утверждает обязательное ожидание email verification при любой регистрации, не описывает media endpoints, необходимые TMDB settings и текущий Vite origin/TTL.

## 8. Изменения для аутентификации по логину и паролю

Базовый сценарий уже реализован текущими локальными изменениями в `ApiModels`, `AuthService`, `UserEntity`, миграции V10 и `App.tsx`; отдельный happy-path тест тоже уже существовал до аудита. Рабочий запрос:

```http
POST /v1/auth/register
Content-Type: application/json

{"username":"new_login","password":"ExamplePass123!"}
```

Затем `POST /v1/auth/login` с теми же username/password возвращает Bearer access/refresh, либо FE сразу использует tokens из register.

Необходимые изменения для завершённого сценария:

1. Исправить B02: занятый логин должен давать понятную ошибку, а FE не должен показывать сообщение «Аккаунт создан» для несуществующей регистрации.
2. Исправить B03 во всех трёх точках работы с паролем. Зафиксировать длину, Unicode и стратегию перехода для старых длинных паролей; не менять алгоритм хеширования без совместимости с существующими аккаунтами.
3. Согласовать канонизацию username и обеспечить её уникальность в БД новой миграцией. До создания ограничения проверить дубликаты. Email-only login можно сохранить для совместимости; поведение при передаче одновременно username/email надо документировать или валидировать.
4. Разделить смысл «email подтверждён» и «можно войти без email»: сейчас у пользователя без email устанавливается `emailVerified=true`, чтобы пройти общий guard. Это работает, но семантика должна быть зафиксирована до добавления привязки email.
5. Завершить FE session lifecycle (B10). Срок access сейчас 30 минут по default; клиент не должен декодировать внутренний формат токена как JWT. При необходимости добавить `expiresAt/expiresIn` в контракт.
6. Определить продуктовый сценарий потери пароля без email. Практический вариант — опциональная привязка подтверждённого email и смена пароля с проверкой текущего; таких authenticated endpoints сейчас нет. Если восстановления не будет, это нужно явно согласовать с PM.
7. Дополнить тесты: занятой логин, Unicode/граница пароля в байтах, гонка регистрации с разным регистром, конкурентные login, повторный refresh на FE, восстановление страницы с истёкшей/отозванной сессией.

## 9. Ограничения эксплуатации и план приёмки

По коду обнаружены дополнительные ограничения, не воспроизведённые как нагрузочные аварии:

- Rate limiter хранится в памяти одной JVM; другой backend в текущей реализации не поддержан. Настройка произвольного `APP_SECURITY_RATE_LIMIT_BACKEND` не добавит Redis. Нужен общий limiter или ограничение на gateway перед несколькими BE instances.
- Поиск/discover/recommendations каждый раз обращаются к TMDB, общего response cache нет. У деталей есть БД-кэш; refresh обрабатывает 25 записей за суточный цикл по default. FAILED/PENDING имеют приоритет; постоянно ошибочные записи могут задерживать остальные. Нужны backoff/nextAttemptAt и проверка достаточности batch/frequency.
- Создание review допускает placeholder до подтверждения TMDB; отказ TMDB не отменяет review. Это подтверждённое предусмотренное поведение, но без отдельного статуса FE может воспринимать неподтверждённую карточку как проверенную. Подлинность существования произвольного ID сейчас не гарантируется.
- Не проводились нагрузочная проверка, проверка нескольких экземпляров, целевого reverse proxy/TLS, реального PostgreSQL, live SMTP/TMDB, browser E2E и анализ уязвимостей зависимостей по advisory-базам.

Порядок работ для команды:

1. Устранить B01–B03 и согласовать username/password/recovery контракт.
2. Исправить B04–B09, добавить регрессионные тесты ожидаемого поведения. Для B09 сначала выбрать формат enum, затем привести к нему тест/документацию/FE.
3. Закончить FE refresh и reviews, обновить README/OpenAPI, убрать или изолировать неиспользуемые шаблонные API helpers.
4. Поднять отдельный PostgreSQL стенд: новые миграции, V9→V10 с данными, CRUD, каскады, гонки регистрации/review/refresh, повторный запуск с validate.
5. На согласованном тестовом стенде с ключом выполнить TMDB movie/TV/search/discover/recommendations, холодный и тёплый cache, локализацию, ошибки и квоты. Настроить SMTP и согласовать тестового получателя перед реальной отправкой verification/recovery.
6. Выполнить браузерный проход: register → profile → catalog → detail → review/rating → answers → refresh → logout; отдельно email verification и recovery, CORS production origin и маршруты ссылок из писем.

До выполнения последних пунктов корректный статус для PM — **локальный аудит выполнен, полная интеграционная приёмка заблокирована настройкой стенда и перечисленными дефектами**.

## 10. Как повторить проверки

Из корня проекта:

```powershell
mvn -B test
mvn -B -DskipTests package
node docs/audit/backend-smoke.mjs
./docs/audit/database-probe.ps1
```

`backend-smoke.mjs` намеренно завершает работу с кодом 1, пока найденные несоответствия существуют. Он не является тестом, который считает баг «успехом». Идентификаторы проверок `BUG ...` и предложенные ожидания остаются видимыми в JSON. Миграции H2 запускаются с validate, без обхода Flyway и без изменения пользовательской БД.

Отдельно проверить HTTP-клиент:

```powershell
mvn -B '-Dtest=TmdbHttpClientFailureTest' test
```

Из каталога frontend:

```powershell
npm.cmd run build
npm.cmd run test:run
```

Диагностический Java probe берёт classpath из Surefire XML после `mvn test`, поэтому отдельные библиотеки скачивать не нужно. Для smoke runner нужны Java в PATH, Node с поддержкой `import.meta.dirname` и предварительно собранный jar. Полные runtime-логи находятся в `target/audit-*.log`; для передачи PM достаточно этого отчёта и `docs/audit/http-results.json`.
