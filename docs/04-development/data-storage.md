# Хранение данных

> **Цель:** описать сущности БД и требования к надёжности хранения · **Обновлено:** 23.10.2026 · **Ответственный:** Иван Зуев (BE)

Источник истины по схеме — миграции и сущности в репозитории бэкенда. Здесь — логическая модель.

## Сущности

| Сущность | Ключевые поля |
|---|---|
| Пользователь | id, логин, хеш пароля, роль, никнейм, о себе, аватар, баллы, дата регистрации |
| Сессия | id, пользователь, refresh-токен (хеш), срок действия, последняя активность |
| Фильм | id TMDB, название, год, длительность, жанры, режиссёр, описание, постер (кэш из TMDB) |
| Автор | id, имя (уникально), специальность, связанный аккаунт, подтверждённые фильмы |
| Оценка | пользователь, фильм, 5 параметров (1–10), итог; одна на пару пользователь — фильм |
| Рецензия | id, пользователь, фильм, заголовок, текст (150–10 000), спойлер, статус модерации, дата; одна на пару пользователь — фильм |
| Лайк рецензии | пользователь, рецензия |
| Лайк автора | автор, рецензия |
| Авторский комментарий | автор, фильм, заголовок, текст, дата; один на пару автор — фильм |
| Предпочтение | пользователь, тип (фильм / режиссёр / актёр), объект; до 5 в каждом типе |

Убрано из старой схемы: почта при регистрации (до согласия на обработку персональных данных) и ответы на рецензии (нет в MVP).

## Надёжность

- **Целостность:** связанные изменения — в одной транзакции (например, рецензия + пересчёт оценки фильма + начисление баллов).
- **Резервные копии:** ежедневные полные копии БД, хранение не менее 7 дней.
- **Сбои:** автоматический перезапуск СУБД и бэкенда; регулярная проверка целостности.
- **Безопасность:** пароли — только хеш; в кэш не попадают персональные данные и токены.
