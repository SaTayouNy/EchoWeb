## 1. Интеграция фронтенда и бэкенда

**Желаемый результат:** сайт работает на данных бэкенда: вход, регистрация, просмотр фильмов и рецензий, оценки, рецензии, лайки, предпочтения и профиль сохраняются в БД.

**Требования:**
- Все запросы — только через `src/api.js`; остальной код фронта не меняется.
- Сопоставление запросов и порядок — по [странице интеграции](../04-development/api-integration.md); после каждого шага обновить статус в её таблице.
- Авторизация через Bearer-токены: access прикрепляется к запросам, при `401` — одна попытка обновить токен и повторить запрос.
- Недостающие на бэкенде эндпоинты чтения (`/authors`, `/people`, `/users`) временно возвращают пустые списки, чтобы сайт загружался.
- Эхо Studio: если роль автора, лайк автора и авторский комментарий не готовы к 27.10 — кабинет закрывается до релиза, решение фиксируется в логе решений.
- Бизнес-правила проверяет сервер: 150–10 000 символов, одна рецензия на фильм, топ-5, права автора.

**Формат результата:** PR в `develop` с изменениями `src/api.js` и бэкенда; обновлённая таблица на странице интеграции; видео или скриншоты прохождения сценариев.

## 2. Состояния интерфейса

**Желаемый результат:** на каждом экране с данными пользователь видит загрузку, результат, пустое состояние или ошибку — интерфейс не выглядит сломанным.

**Требования:**
- Состояния и тексты — по [состояниям интерфейса](../03-product/ui-states.md).
- Загрузка: индикатор на месте контента; кнопки отправки неактивны во время запроса.
- Пустые состояния с действием («Перейти в каталог», «Оставьте первую рецензию»).
- Оптимистичные действия (лайк, лайк автора, предпочтения) откатываются при ошибке с уведомлением.
- Черновик рецензии сохраняется при любой ошибке и при переходе ко входу.

**Формат результата:** PR в `develop`; скриншоты состояний главной, каталога, фильма, формы рецензии и профиля.

## 3. Мобильная заглушка

**Желаемый результат:** на телефоне вместо сломанной вёрстки человек видит аккуратный экран, понимает, что такое «Эхо», и может перейти на лендинг или в соцсети.

**Требования:**
- **Когда показывать:** ширина окна < 768 px **или** телефон по User-Agent. Планшеты (≥ 768 px, в том числе iPad в обеих ориентациях) получают обычный сайт.
- Проверка при загрузке и при изменении размера окна или ориентации: при переходе через 768 px заглушка появляется или скрывается без перезагрузки.
- Заглушка перекрывает весь сайт; под ней не грузятся тяжёлые данные (запросы к API не выполняются, пока показана заглушка).
- **Состав:** логотип «Эхо»; одна фраза о продукте («Платформа для осмысленных рецензий на кино»); текст «Сайт пока работает на компьютере и планшете. Откройте его там — а пока загляните к нам:»; кнопки «Лендинг для авторов», «Telegram», «VK»; кнопка «Скопировать ссылку на сайт» (с уведомлением «Ссылка скопирована»).
- Ссылки берутся из одной константы в коде; пустая ссылка — кнопка не показывается.
- Оформление в стиле сайта: тёмный фон, шрифты и цвета продукта; текст ≥ 16 px; области нажатия ≥ 44×44 px; без горизонтального скролла от 320 px.
- Работает в Safari iOS, Chrome Android, Яндекс Браузере на телефоне; при альбомной ориентации телефона заглушка тоже показывается и читается.
- Событие `mobile_stub_view` отправляется один раз за визит (см. [план аналитики](../05-business/analytics-plan.md)).
- Параметр `?desktop` в адресе отключает заглушку — для отладки и для тех, кто хочет открыть сайт всё равно.

**Формат результата:** PR в `develop`; скриншоты на ширинах 320, 375, 414 px и в альбомной ориентации; проверка на iOS и Android (реальное устройство или эмулятор).

## 4. Обработка ошибок

**Желаемый результат:** любая ошибка сервера или сети даёт понятное сообщение по-русски и путь дальше; данные пользователя не теряются.

**Требования:**
- Бэкенд отдаёт ошибки в едином формате `{ error: { code, message, details } }`, `message` — по-русски; ошибки валидации — с указанием поля в `details`.
- Фронт обрабатывает коды по таблице из [состояний интерфейса](../03-product/ui-states.md): нет сети, таймаут > 10 с, 400, 401, 403, 404, 409, 500.
- Ошибка показывается в месте действия (поле формы, уведомление), а не только в консоли.
- Бэкенд логирует ошибки сервера и внешних API (TMDB), без паролей и токенов в логах.
- Недоступность TMDB не роняет страницу: показываются сохранённые данные или заглушки.

**Формат результата:** PR в `develop` (FE и BE); таблица «код → что видит пользователь» с отметками проверки.

## 5. Яндекс.Метрика и Google Analytics 4

**Желаемый результат:** с первого дня после релиза собираются данные для NSM, воронок и отчётов партнёрам.

**Требования:**
- Счётчики подключены, идентификаторы — в переменных сборки; на `localhost` и staging события не отправляются.
- События и параметры — по [плану аналитики](../05-business/analytics-plan.md); отправка из одной функции-обёртки.
- Цели и воронки в Метрике: активация, рецензия, партнёры. Вебвизор включён.
- В событиях нет персональных данных и текстов рецензий.
- В подвале сайта — короткое уведомление об использовании cookie и аналитики.

**Формат результата:** PR в `develop`; скриншоты событий в режиме отладки Метрики и DebugView GA4.

## 6. Хостинг и выкладка

**Желаемый результат:** продукт доступен по HTTPS на своём домене; есть staging для тестирования.

**Требования:**
- VPS в РФ (Linux, от 2 vCPU / 4 ГБ), домен, HTTPS через Let's Encrypt с автопродлением.
- nginx: статика фронта и `/api` → бэкенд, по [инструкции выкладки](../04-development/deploy.md). Лендинг для авторов — на своём домене.
- Бэкенд — systemd-сервис с автоперезапуском; PostgreSQL; секреты — в переменных окружения.
- Ежедневная резервная копия БД, хранение 7 дней; проверено восстановление из копии.
- Staging из ветки `develop`, продакшен — из тега на `main`.

**Формат результата:** адреса staging и продакшена; инструкция выкладки обновлена; доступы — у PM (не в репозитории).

## 7. Интеграционное тестирование и go / no-go

**Желаемый результат:** команда уверена, что ключевые сценарии работают, и 30.10 принимает решение о запуске.

**Требования:**
- Прогон [чек-листа сценариев](../04-development/testing.md) на staging: гость, зритель, автор, админ, сессия.
- Совместимость: Chrome, Яндекс Браузер, Firefox, Safari, Edge; ширины 1920–1024 и планшет; телефон — заглушка.
- Lighthouse ≥ 70; нагрузочный тест 50–100 пользователей; главная < 3 с.
- Все баги — Issues по шаблону «Баг» с приоритетом; блокирующие закрыты до решения.
- **Go**, если: все сценарии гостя и зрителя проходят, нет блокирующих багов, HTTPS и резервные копии работают, аналитика собирает события. Эхо Studio не блокирует запуск.
- **No-go** — перенос релиза с новой датой и списком причин.

**Формат результата:** отчёт тестирования (таблица сценариев с результатами, список багов) и запись решения go / no-go в [лог решений](../02-management/decisions-log.md).
